# Auto-navigate on a non-empty query, drop the `changed` guard

Type: task
Status: resolved

## Question

Change the auto-navigation rule so it keys on **whether the user typed a query**, not on whether the stack changed. Surfaced at the S3 checkpoint ([ticket 23](23-s3-checkpoint.md)): `<u> a b .set a b` from the address bar did not redirect, because `.set` flips `saved.changed` and the current rule refuses to navigate after any mutation. The user's verdict: the program says "set this, then search `a b`", so it should redirect — *let the user do what the program says*.

**New rule:** auto-navigate iff the run is armed and initial, and the terminal `R` holds **exactly one match with `argDelta ≥ 0`** whose **query is non-empty** (`R.inputs.length > 0`). The `changed` flag drops out of navigation entirely.

Why `R.inputs` is the right discriminator (each verified live against the core this session):

- `<u> a b .set a b` → trailing `.$` consumed `a b` → `inputs: ['a','b']` → **navigates** (the reported defect, now fixed).
- plain search `a b` → `inputs: ['a','b']` → navigates (unchanged).
- `<u> home .set` (no trailing query) → trailing `.$` has no query, matches all targets → `inputs: []` → **shows the list**, so a set with no search still confirms rather than teleporting. Set-intent preserved without a `changed` flag.
- blank open (`?q=` empty / absent) → `inputs: []` → shows the page. This **subsumes** the current `input.length > 0` guard, whose sole job was to stop a one-target store redirecting on a blank open.
- focus-only / focus-driven search (`home .@ .$`, or a blank open resolving stored focus) → focus is **not** part of `inputs`, so `inputs: []` → does not navigate. This preserves today's behavior (focus-setting is a `.@` mutation that never auto-navigated) with no special case.

In scope:

- **`src/client/session.ts`** — rewrite `decideNavigation` to test `terminal[0] === 'R'`, `matches.length === 1`, `match[3].argDelta >= 0`, and `terminal[1].inputs.length > 0`. Drop the `saved`/`changed` checks. The `armed` computation in `run` keeps `mode === 'initial'` and `navigationArmed`; the `input.length > 0` term can go (subsumed by the `inputs` check) — decide during implementation whether to keep it as a cheap short-circuit or remove it; either way its behavior must be covered by a fixture.
- **`src/client/browser-env.ts`** — remove `changed` from `OutputRegister` and stop recording it in `.save`. At the skeleton stage `.save` computed the structural diff *only* for the register, so that computation can be dropped here; [ticket 30](30-bounded-history-and-eviction.md) reintroduces structural-difference detection for **history dedup/eviction** (an internal concern of `.save`, not a register field).
- **Tests** — update `session`/`view` fixtures. Pin: Scenario A redirects; plain search redirects; `home .set` shows the list; blank open shows the page; focus-only search shows the page; incomplete single match (`argDelta < 0`) still renders a clickable link but does not auto-navigate.
- **Docs** — amend `browser-client.md` step 4 and the paragraph after it (the `changed` guard and the `https://example.com/ home .set` worked example), and its `.save` bullet (drop "records `changed` … in the register"). Reword the ticket-15 "never auto-navigate after a mutation" note wherever it's echoed. Write a new **ADR** superseding the changed-guard decision: hard to reverse, surprising without context, a real trade-off (set-and-go vs set-to-confirm) — record that the discriminator is "the user typed a query," realised as `R.inputs`.

Out of scope: S4 history/eviction (tickets 29–33) beyond the `changed`-register removal noted above; any change to `.$`, `inputs`, or `argDelta` semantics (they already carry exactly what this rule needs).

**Done when** the new rule is implemented and tested, `changed` no longer appears in `OutputRegister` or the navigation path, `browser-client.md` and the new ADR describe the query-driven rule with `<u> a b .set a b` as the worked redirect example, and `pnpm verify` is green.

## Answer

Landed on `ticket/34-navigate-on-nonempty-query`; `pnpm verify` green, 287 tests (285 → 287).

**The rule, in one place.** `decideNavigation(register, armed): boolean` became **`resolveNavigationDestination(register): Promise<string>`** in its own small module `src/client/navigation.ts` (review: a boolean threw away the narrowing, so the caller had to re-check `terminal[0] === 'R'` and dig the URL out again). It resolves to the single match's rendered destination when the terminal is an `R` with `matches.length === 1 && argDelta >= 0 && inputs.length > 0`, and rejects otherwise; `main.ts` chains `.then(location.replace).catch(renderView)` on it, scoped so a throw out of `.load` still reaches the bare-error handler. Nothing else is consulted. The `input.length > 0` term in `run`'s `armed` computation was **removed**, not kept as a short-circuit: it was a second statement of the same rule, and its behaviour (blank open with a one-target store shows the page) is pinned by the surviving fixture `never navigates on empty input, even with a single-target state`. **`run`'s `mode` parameter and the `navigationArmed` latch are gone too** (review): `'initial' | 'live'` was redundant with the latch, and the latch itself guarded against a second call to `run` that has no caller — `main.ts` calls it once at load. **Then `session.ts` was collapsed into `main.ts` altogether** (review: with no state left, the session/main split existed only as a test seam; the human did this rewrite by hand). `main.ts` now composes `.load <tokens> .$ .out .save` from the URL, executes it under `navigator.locks` (or bare when absent), and navigates or renders; it stays untested by design, but was boot-probed under happy-dom (`?q=home` against a one-target store → `location.replace`; a throwing `localStorage` → bare error, no navigation). Two bugs were caught and fixed in review of the hand rewrite: helpers declared *after* the synchronous `main()` call hit the temporal dead zone (`Cannot access 'runWithLock' before initialization` on every load), and a `.catch(renderView)` wrapped around the whole chain swallowed the localStorage-unavailable throw. `browser-client.md`'s "once the UI is shown, automatic navigation is disabled" becomes S5's to realise when it adds live execution (noted in the map's S5 fog); the `never navigates in live mode` and `disarms after the first render` fixtures went with the flag.

**`saved` is gone, not just `changed`.** In review the human asked what `env.saved` did; the answer was *nothing* — with the `changed` guard removed it had no reader, and its one future purpose (surfacing a failed write) is served better by `.save` writing its `E(unknown_error)` straight into `env.terminal`, replacing the `R` that `.out` captured. So `OutputRegister` is now `{ terminal, loaded }`; `.save` no longer reads the previous record, diffs, or records anything (`currentStackOf` stays for `.load`). This also closes the "does a failed save suppress navigation" question for free: the failure *is* the terminal, and the rule only navigates on an `R`. Ticket 31's body was reworded accordingly (write the `E` to `terminal`; pin no-navigation with a `session` fixture).

**Fixtures** (`navigation.test.ts` for the rule and the end-to-end run, `browser-env.test.ts` for persistence; `session.test.ts` is gone): the `resolveNavigationDestination` table asserts `resolves` to the URL or `rejects`; it gained `navigates after a mutation` (inputs `['a','b']`, no flag to consult) and `an empty query does not navigate, even to a single complete match`; the `changed`/unsaved/failed-save rows went. End-to-end through the real env + interpreter (compose + execute, then `resolveNavigationDestination`, the steps `main.ts` performs): `set-and-go` (`<u> a b .set a b` → navigates to `https://example.com/`, renders nothing), `set-to-confirm` (`<u> home .set` → list), blank open → page, `home .@` focus-only → page (focus is not in `inputs`), and an incomplete single match (`docs` against `https://example.com/{}`, `argDelta −1`) lists one row with no destination. The `runs inside the lock` fixture went with `session.ts` — lock wiring is `main.ts`'s, untested like the rest of it. Persistence fixtures assert on the stored record instead of `saved`.

**Docs.** [ADR 0009](../../../docs/adr/0009-auto-navigate-on-a-non-empty-query.md) records the decision with the five-row `inputs` table, the rejected options (keep `changed`; gate on raw token count — cannot tell `home .@` from `home`; a `.set`-specific exception — would make the client parse the program against ADR 0007), and the consequences. `browser-client.md` step 4 and its follow-on paragraph now state the query-driven rule with `<u> a b .set a b` as the worked redirect and `<u> home .set` as the worked confirm; the `.save` bullet says a failed save writes its `E` into the register as the terminal. ADR 0007's `.save` bullet gained a parenthetical pointing at ADR 0009. `CONTEXT.md` **Output register** now names only "whether the stored record loaded" as the fact beside the terminal. No "never auto-navigate after a mutation" wording survives outside resolved-ticket history and the map's Decisions-so-far (left as the record of the route).
